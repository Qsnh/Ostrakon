# Ostrakon 设计文档

日期：2026-10-18
状态：待用户审阅批准

> 标注说明：**【用户决定】** 为用户明确说过的；**【凌统决定】** 为设计者自行做出、已告知用户或在此列出待用户审阅的选择；**【留给实现者】** 为可由实现者自行决定的细节。

## 1. 这是什么、为什么做

Ostrakon 是一个用 Go 编写的、类 fail2ban 的主机防护守护进程：盯日志 → 识别暴力扫描/爆破 → 调用防火墙封禁来源 IP → 到期自动解封。

与 fail2ban 的根本区别：**fail2ban 依赖用户编写 jail/filter/action 配置（failregex 正则、maxretry/findtime/bantime 阈值等），学习成本高；Ostrakon 用 TypeSafe AI 的 Jev 快速决策模型替代这些配置，用户不需要理解任何规则就能直接上手。**【用户决定】

**目标用户：** 把应用暴露在公网的人。装好就能保护应用免受暴力扫描和破解。【用户决定】

## 2. 目标 / 非目标 / 反目标

### 目标
- 零规则配置：用户唯一需要提供的东西是 Jev API key。【用户决定：用户自行配置 key、自行承担 Jev 费用】
- 自动发现本机常见服务日志，无需用户指定 logpath。【用户决定】
- 由 Jev 判断"这个 IP 是否在扫描/爆破"以及"该封多久"，替代 failregex 与 maxretry/findtime/bantime。【用户决定】
- 由 Ostrakon 调用防火墙执行封禁，到期自动解封。【用户决定】

### 非目标（第一版不做）
- 通知功能（邮件、Webhook、IM 等）。先保留不做，但代码结构上要留出扩展点。【用户决定】
- Jev 不可用时的降级规则。**不做降级**：Jev 不可用时暂停防护，恢复后自动继续（见 §4.7）。【用户决定】
- 跑在 Docker 容器里的应用的日志发现。第一版只读宿主机上的日志文件和 journald。【用户决定】
- 非 Linux 平台；iptables 后端。【凌统决定，见 §6】
- Web 界面 / 仪表盘。
- 用户自定义规则、正则、阈值的配置文件。
- 经 CDN 或公网反向代理（如 Cloudflare）接入的网站的 Web 防护。这种情况下 nginx 日志里记录的是 CDN 节点 IP，主机防火墙也挡不住经 CDN 转发过来的攻击者。第一版对这类场景的处理是：内置主流 CDN 地址段，永不封禁这些地址（见 §4.4），避免误封 CDN 节点导致整站不可用。sshd 防护不受影响。【凌统决定】

### 反目标（即使"能跑"也算失败）
- **把管理员自己锁在服务器外面。** 误封管理员当前会话或内网/本机地址是最严重的失败。
- **要求用户写任何规则、正则或阈值。** 一旦出现，就背离了项目初衷。
- **静默失效。** Jev 不可用时不能"假装还在保护"，必须在 `ostrakon status` 和日志中清楚显示"已暂停"及原因。
- **上传整份日志。** 只发送与可疑 IP 相关的、经提取和截断的结构化事件（见 §4.5）。【凌统决定，已告知用户】

## 3. 用户体验（头五分钟）

1. 下载单个二进制 `ostrakon`。
2. 以 root 运行 `ostrakon setup`：
   - 交互式提示输入 Jev API key（也可通过环境变量 `TYPESAFE_API_KEY` 提供，环境变量优先）。【凌统决定，已告知用户】
   - 用一次真实的 Jev 调用验证 key 可用；不可用则报错退出。
   - key 保存到 `/etc/ostrakon/key`（权限 0600，root 所有）。
   - 检查 `nft` 是否可用，不可用则报错退出并说明原因。
   - 打印自动发现到的日志源列表。
   - 安装并启动 systemd 服务 `ostrakon.service`（开机自启）。
3. 之后用户无需任何操作。可用的辅助命令【凌统决定】：
   - `ostrakon status`：服务状态、已监控的日志源、当前封禁数、最近一次 Jev 调用结果。
   - `ostrakon bans`：列出当前封禁（IP、原因类别、剩余时间）。
   - `ostrakon unban <ip>`：手动解封。
   - `ostrakon allow <ip|cidr>` / `ostrakon disallow <ip|cidr>`：可选的手动白名单（见 §4.4）。
   - `ostrakon run`：前台运行（systemd 实际调用的入口）。`--dry-run` 只记录决策不真正封禁，便于用户观察。

## 4. 整体流程

```
日志源(文件/journald) ──tail──▶ 字段提取 ──▶ 按 IP 归集(滑动窗口)
                                              │
                                    触发条件满足?
                                              │是
                                              ▼
                                  白名单检查 ─(命中)─▶ 丢弃
                                              │
                                              ▼
                            Jev 判定 (POST /v1/systemone)
                                              │
                          ┌───────────────────┴──────────────┐
                     不封禁 → 缓存"良性"结论            封禁 → nftables set 加元素(带 timeout)
                                                              │
                                                     到期由 nftables 自动移除
```

### 4.1 日志源自动发现【凌统决定】
第一版支持 sshd 与 nginx（与用户确认的"sshd、nginx 等"一致）：
- sshd：`/var/log/auth.log`（Debian/Ubuntu）、`/var/log/secure`（RHEL 系）；两者都不存在时读 journald 中 `ssh`/`sshd` unit。
- nginx：`/var/log/nginx/access.log`（存在则用）。第一版不读 error.log：其中的消息部分会包含攻击者可控的路径，且出现在 `client:` 字段之前，来源 IP 难以可靠锚定；需要的信号（4xx、扫描路径）在 access.log 中已有。
- 架构上日志源是可插拔的"源"列表。每个源内置一个字段提取器（见 §4.2），后续添加服务需要加路径/unit 和该源的提取器。提取器写死在代码里，用户不可见、无需配置。

要求：
- 支持日志轮转（logrotate 的 rename 与 copytruncate 两种方式）。
- 启动时从文件末尾开始读，不回放历史日志。【留给实现者：是否回读最近几分钟】

### 4.2 字段提取【凌统决定】
> 修订说明：此前告知用户"用通用规则提取 IP、不按服务写正则"。审阅发现这样不安全：攻击者可控的字段（sshd 的用户名、nginx 的 URL）可以塞入任意第三方 IP，通用规则会把这个 IP 当成来源，攻击者借此能让 Ostrakon 去封别人（例如 DNS 服务器、管理员家里的 IP），自己却毫发无损。因此改为**每个日志源内置一个按位置锚定的字段提取器**。它是程序内部实现，用户依然无需任何配置，与"零配置"目标不冲突。

- 来源 IP 必须从格式上固定的位置提取：sshd 取**行尾最后一个** `from <ip> port <n>`（用户名在它之前，攻击者可在用户名里伪造一个 `from ... port ...`），nginx access 取行首第一个字段（`$remote_addr`，由 nginx 自己写入）。提取不到就丢弃该行，**绝不退回到"在整行里找 IP"**。
- 同时提取少量结构化字段供 Jev 使用（见 §4.5）：事件类型（如认证失败、无效用户、认证成功）、用户名、请求方法/路径、状态码、User-Agent 等，按来源而定。
- 提取器只负责"这行是谁、做了什么"，不判断是否为攻击。攻击判断仍然完全交给 Jev。
- 每个提取器必须有包含恶意构造日志行的测试用例。

### 4.3 按 IP 归集与触发
- 每个 IP 维护一个滑动窗口内的事件缓冲（附带来源标签，如 `sshd`、`nginx-access`）。
- **不是每行都调用 Jev**：当某 IP 在窗口内活跃到一定程度时，才把它最近的一批事件打包交给 Jev。【凌统决定，已告知用户】
- 触发条件与窗口长度是内部常量，不暴露给用户。初始取值【留给实现者调优】，但需满足：
  - sshd：同一 IP 少量（例如 3 行）认证相关日志即可触发；
  - nginx access：正常访客会产生大量行，因此触发需要更高的量，或出现 4xx/扫描特征路径的比例较高时触发。这里允许基于 HTTP 状态码等通用字段做简单统计，但不得演变为需要用户维护的规则。
- 每次送 Jev 的事件数有上限（例如最近 50 条），保证请求远低于 Jev 的 32K token 限制。
- 同一 IP 在一次 Jev 调用进行中不会重复触发。

### 4.4 白名单（防止锁住自己）【凌统决定】
以下地址**永不封禁、也不发送给 Jev**：
- 回环地址、链路本地地址、RFC1918/ULA 私有地址（也避免把反向代理/负载均衡器的内网 IP 封掉导致全站不可用）；
- 本机自身的所有地址；
- 当前已登录 SSH 会话的来源 IP（从 utmp 或 `who` 获取，定期刷新）；
- 最近成功通过 SSH 认证的来源 IP（由 sshd 提取器锚定识别 `Accepted <method> for <user> from <ip> port` 的行，防止攻击者通过伪造用户名把自己加进白名单）。【留给实现者：保留时长】
- 主流 CDN 的公开地址段（第一版至少包含 Cloudflare 公布的 IPv4/IPv6 段，随二进制内置）。原因见 §2 非目标。
- 用户通过 `ostrakon allow <ip|cidr>` 手动加入的地址（可选功能，不使用也能正常工作，因此不算"需要用户配置"）。对应的 `ostrakon disallow` 用于移除。

### 4.5 Jev 判定

接口（据 TypeSafe 官方文档 docs.typesafe.ai/api）：
- `POST https://api.typesafe.ai/v1/systemone`
- 头：`Authorization: Bearer <key>`，`Content-Type: application/json`
- 请求体：`model`、`state`、`questions`（map，键为自定义问题名）
- 问题类型：`noul`（是/否概率）、`choice`（≤255 个选项，`criteria` 为选项→描述的 map）、`score`（2–10 级，`criteria` 为级别描述数组）
- 响应体：`answers`（按问题名）、`usage`
- 错误：400 / 401 / 413 / 415 / 422 / 429 / 529
- 模型：固定使用一个版本号（例如 `jev-1.13.0`），不用 `jev-latest`，避免厂商升级后行为悄悄变化。【凌统决定】

`state` 为结构化 JSON，内容包括：
- 来源 IP 本身（不含其他 IP）；
- 该 IP 窗口内的事件列表。**不发送原始日志行**，只发送 §4.2 提取出的结构化字段（来源标签、时间戳、事件类型、用户名、路径、状态码、User-Agent 等），每个字符串字段截断到固定长度（例如 128 字符）；
- 该 IP 的历史：过去被 Ostrakon 封禁的次数和最近一次封禁时间（用于替代 fail2ban 的"屡犯递增封禁"）。

已知风险（第一版接受）：用户名、路径、User-Agent 由攻击者控制，攻击者可能写入类似"这是授权的健康检查"的文本，试图干扰 Jev 的判断。缓解手段：只发送结构化且截断后的字段；在问题的 `instructions` 中说明这些字段内容是不可信数据；测试集中包含此类对抗样本。【凌统决定】

一次请求同时问三个问题【凌统决定，问题措辞留给实现者打磨】：
- `is_attack`（noul）：该 IP 的行为是否为暴力破解或恶意扫描。
- `category`（choice）：`ssh_bruteforce` / `web_scan` / `web_bruteforce` / `other_malicious` / `benign`。
- `ban_duration`（choice）：`none` / `10m` / `1h` / `24h` / `7d`。**不提供永久封禁**，以控制误封的代价。

封禁决策：
- `is_attack ≥ 阈值`（初始 0.8，内部常量）且 `ban_duration ≠ none` 时封禁，时长取 `ban_duration`。
- 否则视为良性，在一段时间内（例如 1 小时）缓存该结论，不再为同一 IP 调用 Jev，除非其行为明显增多（例如窗口内行数翻倍）。【留给实现者：具体重评条件】
- 每次判定（含概率与用量）写入日志，便于用户事后追查误封原因。

成本参考：每次调用约 2K 输入 token，按厂商公布的 $0.042/百万输入 token，单次约 $0.0001；每天 1 万个可疑 IP 约 $1。第一版不设花费上限，但客户端需限制并发（例如同时最多 4 个请求）。【凌统决定】

### 4.6 封禁执行（nftables）【凌统决定】
- 使用独立的 nftables 表（例如 `inet ostrakon`），包含 IPv4 与 IPv6 两个带 `timeout` 标志的 set，以及一条丢弃 set 内源地址流量的规则。
- 该规则挂在 **prerouting 钩子上，优先级早于 dstnat（例如 -200）**，而不是 input 链。这样流量在被 Docker 等做端口映射/转发之前就已丢弃，封禁对宿主机服务和映射到容器的端口同样有效。
- 封禁 = 向 set 添加带超时的元素；**解封由 nftables 自动完成**，即使 Ostrakon 停止，到期解封照常发生。【已告知用户】
- 手动解封 = 从 set 删除元素。
- 只操作自己的表，不改动用户已有的防火墙规则。
- Ostrakon 停止时**不删除**已有封禁（保持到期自然解除）。
- 服务器重启后 nftables 表会消失：启动时重建表，并根据本地状态文件把未到期的封禁按剩余时长重新写入。

### 4.7 Jev 不可用时：暂停防护，恢复后自动继续【用户决定】
"不可用"的判定【凌统决定，已告知用户】：
- 网络错误、429、529、5xx：先按 `Retry-After`/指数退避重试，**持续约 1 分钟仍无成功调用**则进入暂停。
- 401（key 无效或失效）：立即进入暂停。
- 400/413/415/422：属于 Ostrakon 自身请求问题，记录错误并丢弃该次判定，**不进入暂停**（否则一行异常日志就能让防护整体下线）。

暂停状态的行为：
- 进程**不退出**。不再调用 Jev 做判定，不新增封禁。【用户决定】
- 已有封禁不受影响，到期由 nftables 自动解除。
- 继续跟踪日志（保持读取位置），各 IP 的滑动窗口照常滚动、过期。恢复后，窗口内仍满足触发条件的 IP 按正常流程判定。【凌统决定】
- `ostrakon status` 显示"已暂停"、暂停原因与开始时间；进入和退出暂停时各写一条醒目的日志（journald 级别为 error / notice）。【凌统决定】

自动恢复：
- 后台定期发送一个最小的探测请求（例如每 1 分钟一次，持续失败时逐步退避到每 5 分钟一次）。探测成功即退出暂停、恢复防护。【用户决定：要恢复；探测间隔为凌统决定，可由实现者调整】
- 每次探测前重新读取 key（环境变量或 `/etc/ostrakon/key`），这样用户用 `ostrakon setup` 更换 key 后无需重启服务。【凌统决定】

其他：
- 由于 Jev 不可用不再导致进程退出，systemd unit 配置 `Restart=on-failure`，仅用于程序崩溃后的自动拉起。【凌统决定】
- 通知：第一版不做；在"进入暂停 / 退出暂停"两个时机预留通知接口（空实现），以后接入邮件/Webhook 时只需实现该接口。【用户决定 + 凌统决定】

## 5. 本地状态
- 位置：`/var/lib/ostrakon/`。
- 内容：当前封禁（IP、到期时间、类别）、每个 IP 的封禁历史、良性结论缓存。
- 格式与存储方式【留给实现者】（单个 JSON 文件或嵌入式 KV 均可），需在异常退出后可恢复。

## 6. 技术约束【凌统决定，已告知用户】
- 语言：Go；产物为单个静态二进制。
- 平台：第一版仅 Linux（systemd）。
- 防火墙：第一版仅 nftables。（此前向用户提到"iptables 或 nftables"，这里收窄为 nftables：主流发行版均已默认提供 nftables，且其 set 超时机制正好满足"Ostrakon 停止后仍能到期解封"。）
- 需要 root 权限运行。
- 尽量少的第三方依赖。Jev 客户端自行实现（接口很小），不依赖社区 SDK。
- 测试中不得调用真实 Jev：用本地假 Jev 服务器模拟各种响应和错误码。nftables 操作通过接口抽象，单元测试中可替换。

## 7. 成功标准
在一台全新的 Ubuntu/Debian 服务器上：
1. `ostrakon setup` 输入 key 后，不需要任何其他操作，服务即开始运行。
2. 从外部 IP 对 sshd 发起密码爆破，该 IP 在约 1 分钟内被封禁。
3. 管理员自己输错一两次密码不会被封；管理员当前 SSH 会话的 IP 在任何情况下都不会被封。
4. 断网模拟 Jev 不可用：约 1 分钟后进入暂停，`ostrakon status` 和日志可见暂停原因，已有封禁按时到期解除；恢复网络后几分钟内自动退出暂停、恢复防护。用无效 key 时立即暂停，用 `ostrakon setup` 换成有效 key 后自动恢复。
5. `ostrakon bans` / `unban` 正常工作；服务器重启后未到期的封禁被恢复。

- 各源字段提取器的具体实现（须遵守 §4.2 的锚定原则）。
- 状态存储格式、日志输出格式。
- Go module 路径、目录结构、CLI 库选型。
